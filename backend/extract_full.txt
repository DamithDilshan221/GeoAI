═══════════════════════════════════════════════════════════════
RESOLVED DESIGN DECISIONS — READ BEFORE BUILDING
═══════════════════════════════════════════════════════════════

1. `name` AND `location_name` ARE DIFFERENT FIELDS — DO NOT COLLAPSE THEM.
   Per §19.3's comment and the worked examples in §6.3: `name` is the
   full, category-qualified display name (e.g. "MA Canteen Washroom
   (Male)"); `location_name` is just the building/place ("MA Canteen").
   Both are required on every seeded facility. `location_name` exists
   specifically to support location/building-name search (v3 §31's note:
   "Search already filters by name/location string") — it is not a
   duplicate of `name`, and validation must not allow it to be blank
   while `name` isn't, or vice versa.

2. MIGRATION 0006 BACKFILLS BEFORE TIGHTENING, EVEN THOUGH THE DEV
   WORKFLOW WILL TRUNCATE AND RESEED ANYWAY. Don't skip the backfill step
   on the reasoning that dev data will be truncated — write the migration
   to be correct for a database with real pre-existing NULL
   `location_name` rows regardless of how you personally plan to use it
   this session, since a future environment (e.g. a teammate's machine
   that already ran Phase 2's correction and seeded old-style data before
   this phase landed) won't get the truncate-and-reseed treatment:
     UPDATE facilities SET location_name = name WHERE location_name IS NULL;
     ALTER TABLE facilities ALTER COLUMN location_name SET NOT NULL;
   Both statements in one migration, backfill first.

3. FIXTURE VALIDATION IS A CONTROLLED VOCABULARY, NOT FREE-FORM JSON. Every
   other enum-like concept in this schema (`facility_status`,
   `data_source`, now `audience_type`) is a real Postgres ENUM specifically
   so a typo can't silently create an unfilterable value. `fixtures` is
   JSONB (it has to be, it's a count map, not a single value) but the
   application-level validation must still reject unknown keys and
   negative/non-integer counts — the schema-level looseness of JSONB is
   not a license for the validation layer to also be loose.

4. `FacilityRepository.create()` GAINS `location_name` AND `audience` AS
   REQUIRED PARAMETERS AND `fixtures` AS AN OPTIONAL ONE (DEFAULTING TO
   `{}`), REPLACING THE REMOVED `capacity`/`accessibility` PARAMETERS
   ENTIRELY — NOT ADDING TO THEM. Confirm the old parameters are actually
   gone from the method signature, not just unused.
